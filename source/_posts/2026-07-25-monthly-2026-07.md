## 这个月的具体账

- 慢查询日志（`long_query_time = 1`）7 月 3 号抓了 **8 条**，其中 **7 条**是索引压根没生效，剩下 1 条是真回表太多。改完书店列表接口的 P99 从 **820 ms 降到 130 ms**，慢查询条数从每天 1400 多条降到 30 几条。
- JSON 解析那段提示词从 **486 字删到 172 字**，一次调用就符合 schema 的比例 **91.4% → 99.7%**，每天的重试从 60 多次降到个位数（7 月 24 号那天只有 2 次），每个请求省下来大概 310 个 token。
- 订单服务单测行覆盖率 **41.3% → 53.1%**，就是标题里那 12 个点。然后查出 **2 个假测试**（一个 `assertEquals(x, x)`，一个把三个依赖全 mock 掉的），删掉后 52.9%；把边界清单和禁止项写进 `AGENTS.md` 重做一遍，到 **57.6%**，分支覆盖 27.8% → 40.1%。PIT 变异得分 34.1% → 61.3%。
- 评测集 **47 条 query、213 个 (query, 相关文档) 标注对**，脚本改到第四版才一次跑完，`recall@5 = 0.617`，耗时 3.2 秒。第一版连 `jsonl` 里一行尾逗号都能崩半小时。

## 踩坑记录

**一、EXPLAIN 里那七条。** 慢的全是 `books` 表，2 万多行，看着不多，可列表接口每次都全表扫。最典型的一条把日期列套了函数：

```sql
-- 改前：对列套函数，idx_created_at 直接废掉
EXPLAIN SELECT id, title, price FROM books
WHERE DATE(created_at) = '2026-07-03' AND status = 'ON_SALE';

-- 改成范围扫描，配合 (created_at, status) 联合索引
ALTER TABLE books ADD INDEX idx_created_status (created_at, status);

SELECT id, title, price FROM books
WHERE created_at >= '2026-07-03 00:00:00'
  AND created_at <  '2026-07-04 00:00:00'
  AND status = 'ON_SALE';
```

```bash
mysql -h 127.0.0.1 -u bookstore bookstore -e "EXPLAIN SELECT id, title, price FROM books WHERE DATE(created_at) = '2026-07-03' AND status = 'ON_SALE';"
# id  select_type  table  type  possible_keys     key   rows    Extra
#  1  SIMPLE       books  ALL   idx_created_at   NULL  182340  Using where
```

改完 `type` 从 `ALL` 变 `range`，`rows` 从 182340 降到 2100 左右。八条里的成因：3 条对列套了 `DATE()`，2 条 `phone = 13800138000` 拿数字查 varchar 触发隐式类型转换，1 条联合索引 `(category_id, status, create_time)` 的查询没带最左列，1 条 `LIKE '%三体%'` 前置通配。最后那条不是索引失效，是回表太多，补了个覆盖索引了事。这一轮最费时间的不是改 SQL，是说服自己别去调 `join_buffer_size`——第一版我确实调了，从 256K 加到 2M，P99 纹丝不动，白折腾一晚上。

**二、把 JSON 提示词删掉半页。** 07-11 那篇写全了，这里只贴最后落地的配置。原来提示词里塞了「请只输出 JSON」「不要加 markdown 围栏」「字段名必须是 title/author/tags」「缺失字段填空字符串」……一共 486 字，还附了三个 few-shot 示例。全删了，换成接口自带的 schema 约束：

```json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "book_extract",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "title": { "type": "string" },
          "author": { "type": "string" },
          "tags": { "type": "array", "items": { "type": "string" } }
        },
        "required": ["title", "author", "tags"],
        "additionalProperties": false
      }
    }
  }
}
```

`strict: true` 要求 `required` 把所有 key 列全、`additionalProperties` 必须是 false，这两个我第一遍漏了，接口直接 400。修完之后解析侧那堆 `strip()`、去围栏、正则捞大括号的代码删了 60 多行。早该这么干。

**三、评测集第四版才跑通。** 第一版脚本用 `jieba` 自己分词算命中，跟线上 IK 分词器口径不一致，跑出来的数跟日志对不上；第二版改成直接读检索服务返回的 `hits`，结果 `jsonl` 里有一行尾逗号，`json.loads` 崩在第 31 行；第三版修好了解析，但 `recall@5` 把「相关文档不足 5 个」的 query 分母算成了 5，整体被压低 4 个点。第四版干脆把分母固定成标注的相关文档数：

```python
#!/usr/bin/env python3
"""tools/eval_keyword.py：关键词检索的 recall@k，输入是人工标注的 jsonl。"""
import argparse
import json
import time
from pathlib import Path


def load_jsonl(path):
    with Path(path).open(encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]


def recall_at_k(hits, relevant, k):
    if not relevant:
        return 0.0
    return len(set(hits[:k]) & relevant) / len(relevant)


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--qrels", default="eval/qrels.jsonl")
    ap.add_argument("--runs", default="eval/keyword_run.jsonl")
    ap.add_argument("--k", type=int, default=5)
    args = ap.parse_args()

    qrels = {r["query"]: set(r["relevant"]) for r in load_jsonl(Path(args.qrels))}
    runs = {r["query"]: r["hits"] for r in load_jsonl(Path(args.runs))}

    t0 = time.perf_counter()
    scores = [recall_at_k(runs.get(q, []), rel, args.k)
              for q, rel in qrels.items()]
    print(f"{len(scores)} 条 query，recall@{args.k} = "
          f"{sum(scores) / len(scores):.3f}，"
          f"耗时 {time.perf_counter() - t0:.1f}s")


if __name__ == "__main__":
    main()
```

`python3 tools/eval_keyword.py --k 5` 现在输出 `47 条 query，recall@5 = 0.617，耗时 3.2s`，一次过。这脚本我塞进 CI 了，每周一跑一次基线，防止有人改了分词词库悄悄把数拉下去。
