那天从坐下到能跑通第一条 GraphQL 查询，花了 38 分钟，其中大概 30 分钟在找哪个进程占端口。9 月 8 号早上 9 点 20，我第 N 次按顺序起环境：`mysqld`、`redis-server`、装了 pgvector 的那个 Postgres、OTel Collector，折腾完才轮到 `node`。敲到第二条就卡住了：

> `$ redis-server --port 6379`
> `21740:C 08 Sep 09:20:31.442 # Warning: no config file specified, using the default config.`
> `21740:C 08 Sep 09:20:31.443 # Failed listening on port 6379 (tcp), aborting.`

上周调试完 `docker run` 的那个 Redis 容器还挂着，端口占着没还。9 月这篇月报的两件事，都是从这类破事里长出来的。

## 具体账

- **09-05 OTel**：`featuredBooks` 从 1812ms 降到 210ms，31 条串行 SQL 收成一条批量查。field-level span 全开时单条 trace 486 KB、Collector 内存顶到 1.7 GB 被 kill，关掉之后 14 KB；采样率定在 0.2，Jaeger 留 3 天。
- **09-12 文案**：全仓扫出 47 处硬编码的英文用户文案，改了 41 处，剩 6 处是第三方 SDK 抛出来的，包了层转换函数兜住。`extensions.code` 统一成 18 个英文常量。脚本塞进 CI 之后两周，新增 0 处。
- **09-19 compose**：5 个服务（MySQL 8.0.39、pgvector/pgvector:pg16、Redis 7.2.5、otel-collector 0.102.1、Jaeger 1.57），`compose.yaml` 一共 127 行。第一次拉镜像 3 分 40 秒，之后 `docker compose up -d` 到全部 healthy 是 9 秒；以前手动起是 5 条命令、5 个终端、平均 30 多分钟（含找端口的时间）。
- 宿主端口统一挪开：Redis 6380、Postgres 5433、MySQL 3307，避开各种残留进程。`REDIS_URL` 之类的配置跟着改了一轮。

CI 那条脚本跑一次 2.3 秒，挂在 `lint` 阶段后面，MR 里多一行英文 toast 直接红灯。第一次挂上去就把我自己拦了一次：`throw new GraphQLError('Item added')` 写完顺手提交，CI 秒红，回去改成 `已加入购物车`。规矩光靠文档写一遍没用，得有个东西在提交时拦一下。

## 踩坑记录

**一、`depends_on` 只等容器起来，不等服务能连。** 第一版 compose 写 `depends_on: [postgres]`，应用一启动就报：

> `psql: error: connection to server at "postgres" (172.20.0.2), port 5432 failed: FATAL: the database system is starting up`

`depends_on` 默认等的是 `service_started`，容器进程一跑就算数，Postgres 自己还在 initdb。换成 `condition: service_healthy` 加 `pg_isready` / `redis-cli ping` / `mysqladmin ping` 的 healthcheck 才消停。这个报错文本我搜了半天，一开始还以为是密码写错了。

**二、init 脚本只在数据卷为空时跑一次。** 我给 `init/001-schema.sql` 加了两个字段，`docker compose restart` 之后 `\d books` 一看还是旧表。翻文档才想起来 `/docker-entrypoint-initdb.d/` 只在第一次创建卷时执行。想让改动生效得 `docker compose down -v` 把卷删了重来——这个 `-v` 会把本地测试数据一起清掉，我第一次敲之前没备份，赔进去半天的造数据脚本。（后来把造数据挪成了 `tools/seed.py`，`down -v` 之后跑一下就回来，这次算长记性了。）

**三、端口残留。** 就是开头那幕。compose 里宿主端口全挪开，并且规定 `docker compose down` 才算收工，不许 `Ctrl-C` 了事。

**四、扫描脚本第一版误报 200 多条。** 把 `Content-Type`、`Accept-Encoding` 这些 HTTP 头、`console.log` 里的英文调试信息、还有 `SELECT` 语句全当成「给用户看的文案」报出来了。收窄到只扫 `GraphQLError(...)`、`message:` 和 `toast.error(...)` 三处调用之后，才从 200 多收敛到 47。

**五、`down -v` 差点把同事的数据一起清了。** 上面第二条里删的是我自己机器上的卷，后来把 compose 推给同事，有人在共享开发机上照着 `down -v` 敲了一遍，把那台机器上别人造的测试数据也带走了。现在 README 里加了行加粗的「`-v` 只在你确定卷里没别人东西时用」，并且把常用命令收进 `Makefile`：`make up` 不带 `-v`，`make reset` 才带。危险命令本来就不该写进日常步骤里。

## 文案规矩是怎么落地的

4 月重写 Schema 那篇里定过一句「中文给人看，英文给机器看」，09-05 接 OTel 时又在 README 里写死了一遍（span 名、错误码、attribute key 全英文，弹给用户那句话用中文）。可一直只是句约定，没人盯。12 号把它扩到全仓，先写了个脚本把存量捞出来：

```python
#!/usr/bin/env python3
"""扫 src/ 下抛给用户看的字符串，含英文字母的报出来。"""
from pathlib import Path
import re

root = Path("src").resolve()
pat = re.compile(
    r"""(?:GraphQLError|message|toast\.(?:error|info))\s*\(?\s*['"]([^'"]+)['"]"""
)
hit = 0
for p in sorted(root.rglob("*.ts")):
    for lineno, line in enumerate(p.read_text(encoding="utf-8").splitlines(), 1):
        for text in pat.findall(line):
            if re.search(r"[A-Za-z]", text) and not text.startswith(("http", "/")):
                print(f"{p.relative_to(root)}:{lineno}:  {text}")
                hit += 1
print(f"共 {hit} 处")
```

```bash
$ python3 tools/check_i18n.py
errors/OrderErrors.ts:18:  Order not found
resolvers/book.ts:44:  Book not found
resolvers/cart.ts:91:  Failed to add item
...
共 47 处
```

改的时候也纠了几处「英文没写全但更别扭」的，比如 `操作成功!` 那个半角叹号，一并换成 `加入购物车成功`。真正麻烦的是分类：有些字符串看着像给用户看的，其实是 `extensions.code` 或者日志的 `level`，这些按规矩保持英文，脚本靠白名单放过去。规矩说起来就一句话，落到「哪根字符串归哪类」还得逐条看，47 处我过了两遍。

剩 6 处第三方 SDK 抛的没硬改，写了个 `toUserMessage(err)`：拿 `err.code` 查一张中文映射表，查不到就回退到一句通用的 `操作没成功，请稍后再试`。没去 fork 人家的包，也没在业务代码里到处 `if (err.message === '...')` 判字符串——那种判法 4 月踩过一次，SDK 升级改了个标点就全失效。

## 一个 compose.yaml 收了 5 个中间件

```yaml
name: bookstore-dev

services:
  mysql:
    image: mysql:8.0.39
    environment:
      MYSQL_DATABASE: bookstore
      MYSQL_ROOT_PASSWORD: dev_only
    ports:
      - "3307:3306"
    volumes:
      - mysqldata:/var/lib/mysql
      - ./init/001-schema.sql:/docker-entrypoint-initdb.d/001-schema.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -pdev_only --silent"]
      interval: 2s
      timeout: 3s
      retries: 20

  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: bookstore_vec
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev_only
    ports:
      - "5433:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dev -d bookstore_vec"]
      interval: 2s
      timeout: 3s
      retries: 20

  redis:
    image: redis:7.2.5-alpine
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "6380:6379"
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 3s
      retries: 20

  jaeger:
    image: jaegertracing/all-in-one:1.57
    environment:
      COLLECTOR_OTLP_ENABLED: "true"
    ports:
      - "16686:16686"

  otel-collector:
    image: otel/opentelemetry-collector-contrib:0.102.1
    command: ["--config=/etc/otelcol-contrib/config.yaml"]
    volumes:
      - ./otel/collector.yaml:/etc/otelcol-contrib/config.yaml:ro
    ports:
      - "4317:4317"
      - "4318:4318"
    depends_on:
      - jaeger

volumes:
  mysqldata:
  pgdata:
  redisdata:
```

`Running 9/9` 是 5 个容器加 1 个网络加 3 个卷，别数错了，我第一次看也愣了一下。`otel/collector.yaml` 直接复用 09-05 那篇里的那份，一个字没改。应用侧读 `DATABASE_URL`、`REDIS_URL`、`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` 三个环境变量，宿主端口改了之后把 `.env.example` 同步一遍就完事。

`healthcheck` 的 `retries: 20` 配 `interval: 2s`，等于最多等 40 秒，Postgres 第一次 initdb 大概 8 秒，够用；Redis 那条用 `redis-cli ping` 判 `PONG`，容器里没装 `curl` 也能跑。MySQL 那条 `mysqladmin ping` 有个小陷阱：密码写错它也返回「服务活着」，所以健康只代表端口通了，账号对不对还得应用自己连一次才知道，我第一次就被这个骗过，对着 `Access denied` 查了十分钟。
