8 月 14 号晚上 10 点 11 分，群里甩来一句「订单详情页的实时状态又卡住了，刷新一下就好」。我登上测试机，用 `curl -Ns` 挂着那条 SSE 流打时间戳，从 `22:11:03` 数到 `22:12:03`，正好第 60 秒，连接干净利落地断了：

```bash
$ curl -Ns http://127.0.0.1/api/orders/ord_88231/stream | while IFS= read -r line; do printf '%s  %s\n' "$(date +%T)" "$line"; done
22:11:03  data: {"orderId":"ord_88231","status":"PAID"}
22:12:03  curl: (56) Recv failure: Connection reset by peer
```

前端那边已经改了三版：`EventSource` 自动重连、退避重连、断线时补一次全量查询。三版都能「刷新一下就好」，也都在第 60 秒准时再断。我一开始也顺着浏览器那条线查了半天，直到把 `curl` 直接打到 Nginx 上（绕过前端）复现出一模一样的 60 秒，才反应过来锅根本不在浏览器里。

## 具体账

- **tRPC 那次没落地**。挑了 `bookById` 和 `addToCart` 两个接口试了 3 天，TypeScript 端确实舒服：GraphQL codegen 生成的 `src/generated/graphql.ts` 是 3417 行，tRPC 这边一行生成物都没有，`router` 定义完前端直接 `import type` 就有提示。可小程序那套是原生 JS，不吃这套类型；再加上 `extensions.code` 那 18 个错误码常量得重新设计一遍，算下来收益撑不住迁移成本。试完把分支标了个 `experiment/trpc` 就没再动，主仓还是 Apollo Server 4.10.0。
- **订单状态**：JDK 21，`sealed interface OrderState` 配 6 个 `record` 实现，原来那个 `enum` + 11 处 `switch` 收敛到 3 处，状态相关的类从 214 行降到 96 行。
- **SSE**：`proxy_read_timeout` 从默认 60s 调到 300s，应用侧补了 20 秒一次的 `: ping` 注释心跳。改完挂了一台机器观察 3 天，前端上报的重连次数从每天 400 多次降到 0。
- **书名检索**：MySQL 的 `LIKE '%...%'` 换成 `BAAI/bge-small-zh-v1.5`（512 维）存进 PostgreSQL 16 + pgvector 0.7.4。评测集从 80 条扩到 240 条，Recall@10 从 0.68 到 0.87；代价是 P95 从 12ms 涨到 45ms，后来给热门 query 加了层 Redis 缓存，回落到 18ms。
- `hexo generate` 冷启动还是 1.9s，没变。这月新增的两个 SVG 图一共 9 KB。

归档页那块顺手改了下：`lead` 字段其实 4 月就写进 front-matter 了，但模板一直没渲染，等于白写。现在每篇卡片下面多一行 TL;DR，动了 2 个 EJS 文件，`hexo generate` 从 1.9s 变成 2.1s。多出来的 0.2s 认了，总比点进去才知道讲什么强。

## 踩坑记录

**一、60 秒是个太整的数字。** 整到不可能是巧合。翻 `nginx -T` 看到 `proxy_read_timeout 60s`（Nginx 默认值，我们从来没显式写过），上游在订单没新状态时是静默的，60 秒等不到一个字节就断开。更阴的是 `proxy_buffering` 默认 `on`，就算上游偶尔吐点东西也会被攒在缓冲区里不往客户端送。前端三版重连全在治标。（顺带一提，`X-Accel-Buffering` 这个响应头我之前压根不知道有这东西。）

```bash
$ cat > /etc/nginx/conf.d/sse.conf <<'EOF'
location /api/orders/ {
    proxy_pass         http://order_service;
    proxy_http_version 1.1;
    proxy_set_header   Connection "";
    proxy_buffering    off;
    proxy_cache        off;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
EOF
$ nginx -t && nginx -s reload
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

$ curl -Ns http://127.0.0.1/api/orders/ord_88231/stream | while IFS= read -r line; do printf '%s  %s\n' "$(date +%T)" "$line"; done
22:41:07  data: {"orderId":"ord_88231","status":"PAID"}
22:41:27  : ping
22:41:47  : ping
22:46:07  : ping
```

最后那行是 5 分钟之后，连接还活着。应用侧的心跳我是用 `ScheduledExecutorService` 每 20 秒往 `SseEmitter` 里塞一行 `: ping\n\n`，注释行不会触发前端的 `onmessage`，纯粹是给中间每一跳续命。只调 Nginx 不放心，光加心跳又绕不开缓冲，两边一起动才踏实。

**二、record 不能改字段，我撞了一次。** 第一版把 `paidAt` 和 `updatedAt` 都写进 `Paid` 这个 record，后来想在处理逻辑里更新 `updatedAt`，编译器直接甩 `cannot assign a value to final variable updatedAt`。愣了两秒才想起来 record 是不可变载体，压根没打算让你改。最后状态只留 `paidAt`，把「最后一次变更时间」挪到外层的 `OrderStateChanged` 事件里。少了一半样板代码是真的，但「什么该进状态、什么该进事件」这个不起眼的设计问题，我改了两遍才顺过来。还有一次加新状态 `Refunding` 忘了写进 `permits`，`javac` 报 `class Refunding is not allowed to extend sealed interface OrderState`，倒比运行时炸出来强。

**三、tRPC 的类型共享没覆盖到小程序。** 上面账里写了。补一句：那个分支里 `pnpm tsc --noEmit` 是全绿的，类型对得严丝合缝，问题出在「谁在消费这份契约」上——跟 4 月重写 Schema 时踩的是同一件事，只不过那次是页面用例，这次是端侧语言。顺带一提，tRPC 的 `createCaller` 写服务端内部调用挺顺手，这个以后可能单独用用。

**四、评测集原来全是「标准答案」。** 80 条里清一色是完整书名，比如「三体Ⅱ·黑暗森林」。换成向量检索以后，该测的其实是用户会怎么搜，不是库里存了什么。我把 80 条改成 240 条：40 条精确书名、80 条口语 query（「那个黑暗森林」「刘慈欣第二部」「讲宇宙的科幻」）、60 条带错别字和罗马数字变体、60 条完全不相关的负例。第一版重写完 Recall@10 只有 0.71，比预期的低一大截，查出来是负例里混进了 11 条其实相关的（「三体」系列互相算相关），清掉之后才到 0.87。

## 那段向量查询和评测脚本

线上查询长这样，`<=>` 是 pgvector 的余弦距离，阈值 0.35 是拿评测集扫出来的，不是拍的：

```sql
-- book_embeddings(book_id text primary key, title text, embedding vector(512))
-- 先按书名向量召回 20 条，再用原来的库存/上下架条件过滤
WITH candidates AS (
  SELECT book_id, title,
         embedding <=> $1::vector AS distance
  FROM book_embeddings
  ORDER BY embedding <=> $1::vector
  LIMIT 20
)
SELECT c.book_id, b.title, b.price_cents, c.distance
FROM candidates c
JOIN books b ON b.id = c.book_id
WHERE c.distance < 0.35
  AND b.status = 'ON_SHELF'
ORDER BY c.distance;
```

```python
#!/usr/bin/env python3
"""算 Recall@10：评测集每行是 query\t相关书 id 列表（逗号分隔）。"""
import json
from pathlib import Path
import psycopg2
from tools.embed import embed  # bge-small-zh-v1.5，输出 512 维

cases = [
    (q, set(ids.split(",")))
    for q, ids in (line.rstrip("\n").split("\t")
                   for line in Path("eval/queries.tsv").read_text(encoding="utf-8").splitlines()
                   if line and not line.startswith("#"))
]

conn = psycopg2.connect("dbname=bookstore user=dev password=dev_only host=127.0.0.1")
hits = 0
for query, relevant in cases:
    vec = embed(query)
    with conn.cursor() as cur:
        cur.execute(
            "SELECT book_id FROM book_embeddings "
            "ORDER BY embedding <=> %s::vector LIMIT 10",
            (json.dumps(vec),),
        )
        top10 = {r[0] for r in cur.fetchall()}
    hits += bool(top10 & relevant)

print(f"Recall@10 = {hits / len(cases):.3f}  ({hits}/{len(cases)})")
```

`psycopg2` 那边 `%s::vector` 传的是 JSON 数组字符串，pgvector 的 Python 侧没装 `pgvector` 包时这么写最省事。第一版我直接把 list 丢进去，报 `can't adapt type 'list'`，查了半小时才改成 `json.dumps`。脚本现在跑一次 240 条要 11 秒，主要耗在逐条算 embedding 上，批量化留到以后。

阈值 0.35 也是拿这 240 条扫出来的：0.30 时召回掉到 0.79，0.45 时混进来一堆不相干的科幻，0.35 是拐点。这数只对自己这批书名成立，换库就得重扫，现在硬写在 SQL 里，等哪天真换了再说。评测集的标注口径比参数更要命——第二版我把「相关」定义成「同一本书的不同版本」，结果 `三体` 和 `三体Ⅱ·黑暗森林` 算不相关，Recall 被自己压下去 0.09。现在 `eval/queries.tsv` 头部钉了 12 行注释写清口径，谁改都得先改注释。
