## 具体账

- `hexo generate` 冷启动从 4 月的 1.9s 涨到 **2.3s**，32 篇共 41 个 HTML 页面。慢在哪没细查，归档页现在是全量渲染，等过 50 篇再说。
- AI CLI：10-08 重写 `AGENTS.md` 之前，加一个 GraphQL query 平均纠偏 **5 轮**、累计 **23k tokens**；58 行上下文塞进去之后平均 **1.2 轮**、**9k**。本月 CLI 累计调用 **214 次**，脚本化之后「加 query」基本不再开新对话。
- 客服 agent：10-23 全天 **1240** 次工具调用，**31** 次超时重发，其中 **17** 次落在 `create_order`。加幂等键之前，那 17 条里出了 **1 起重复下单、2 张单**；回放压测 **200** 次重复调用，改动后只落 **1** 单。
- ES 深翻页：第 800 页（每页 20 条，`from=16000`）撞上默认 `max_result_window=10000`，换 `search_after` + PIT 之后深翻页 P99 从 **4.1s** 降到 **380ms**。过程在 10-17 那篇。
- 库存缓存：想省 Redis QPS，本以为能从 **1200** 降到 **300**，上线 10-28 当天收到 **6 条**「显示有货但下单失败」的客诉，19:40 回滚。下面单说。

AI CLI 那笔 token 账是从网关落的 jsonl 里算的，脚本扔在 `tools/`：

```python
#!/usr/bin/env python3
"""从网关 jsonl 里按需求聚合 token，算每需求累计用量。"""
import json
from collections import defaultdict
from pathlib import Path

usage = defaultdict(lambda: [0, 0, 0])  # 轮数, 输入, 输出

for line in Path("logs/agent-cli-2026-10.jsonl").read_text(encoding="utf-8").splitlines():
    rec = json.loads(line)
    if not rec["date"].startswith("2026-10"):
        continue
    row = usage[rec["task"]]
    row[0] += 1
    row[1] += rec["input_tokens"]
    row[2] += rec["output_tokens"]

total_rounds = sum(r[0] for r in usage.values())
total_tokens = sum(r[1] + r[2] for r in usage.values())
print(f"任务数 {len(usage)}，总轮数 {total_rounds}，总 tokens {total_tokens}")
for task, (n, tin, tout) in sorted(usage.items(), key=lambda kv: -sum(kv[1][1:]))[:5]:
    print(f"{task}: {n} 轮, {tin + tout} tokens")
```

跑出来前几名里，`booksByAuthor` 那个任务是 10-08 之前的，5 轮 23k；重写上下文之后同类任务都是 1 轮 9k 上下，两坨数字挨着，看着挺直观。

## 踩坑记录

**一、四份上下文靠手抄。** `AGENTS.md`、`CLAUDE.md`、`CONVENTIONS.md`、`GEMINI.md` 内容一样，10-09 改过一次构建命令漏同步了 `GEMINI.md`，隔天它又拿 `npm install` 给我上了一课。10-09 还误删过 `OrderResolver.ts`，没提交，`git restore` 一行捞回来的。这两条写在 10-10 那篇了。

**二、幂等键差点又没挡住。** 第一版让模型自己拼 `orderNo`，超时重试它换了个新号，SETNX 两次都过。改成「工具名 + 上游定死的 `checkoutId`」才算真挡住，详情 10-24 那篇。还有个 900 秒 TTL 的坑：用户隔 22 分钟回来点确认，键过期又放了一单，改 24 小时 + 库里唯一索引兜底。

**三、ES 的「第 800 页」。** 报错原文是 `Result window is too large, from + size must be less than or equal to: [10000] but was [16000]`。一开始想调大 `max_result_window` 糊过去，被同事拦了——深翻页用 `from/size` 本来就不对，换成 `search_after` 配 PIT 才对。

**四、marked 又拆了我的表格。** 有一篇表格单元格里写了 `a | b` 当示例，GFM 直接把它拆成两列。4 月那篇记过一次，这个月又踩，转义 `\|` 才消停。吃一堑没长一智，记在这里，下次别再犯。

## 那次没做成的新手优化

10-28 那天我看 `query_stock` 一天被调 1200 次，手一痒给它套了层进程内缓存，想着省掉大半 Redis 读：

```ts
// 已回滚，别照抄
const stockCache = new Map<string, { qty: number; at: number }>();
const TTL_MS = 60_000;

export async function queryStock(sku: string): Promise<number> {
  const hit = stockCache.get(sku);
  if (hit && Date.now() - hit.at < TTL_MS) {
    return hit.qty; // 就是这行出的事
  }
  const qty = await redis.get(`stock:${sku}`);
  stockCache.set(sku, { qty: Number(qty), at: Date.now() });
  return Number(qty);
}
```

问题一眼能看出来：库存是会被订单扣减的，进程内这 60 秒里谁都改不到它。用户问「还有货吗」，agent 拿缓存回「有」，转头 `create_order` 去扣减才发现实际 0 件，回一句下单失败。19:40 回滚：

```bash
$ git revert --no-edit 3f1c8a2

 1 file changed, 14 deletions(-)
$ pnpm typecheck
Found 0 errors.
$ grep -c '显示有货但下单失败' logs/cs-2026-10-28.log

```

教训不新鲜，但我当时真觉得「只读查询加缓存能有啥事」。它跟 10-24 那篇里「只读工具别进幂等」其实是同一个毛病换了个长相：库存这种东西，正确性比省那点 QPS 要紧。1200 降到 300 的账我算得挺美，6 条客诉没算进去。回滚之后没再动，先把 `stock:` 这个键的更新链路看明白再说。

这个「优化」从写完到回滚不到 7 小时，PR 描述我写的是「小幅降低库存查询延迟」，现在回看挺讽刺的。（还好回滚走的是 `git revert`，没手贱 `reset --hard`——上月刚在组里说过别这么干。）
