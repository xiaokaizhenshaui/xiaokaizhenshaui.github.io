6 月 19 号 02:14，手机震了一下，Grafana：`jvm_memory_used{area="heap"} > 92%`，持续 4 分钟。摸到电脑、连上 VPN，容器已经重启过一轮，`kubectl describe pod` 里写着 `Last State: Terminated, Reason: OOMKilled`。想抓 heap dump 才发现 `-XX:HeapDumpPath` 指的那个卷只剩 1.2 GB，而 4 GB 的堆真 OOM 时 dump 是 2.7 GB——写到一半失败，留下半个文件。那晚等于什么都没查到，只能等第二次。

这个月差不多是这么劈成两半的：前半段在量 GraphQL 为什么慢，后半段在补 dump 的坑。中间还有一周，本来该发一篇，没写出来。

## 这个月的具体账

- **DataLoader**：书架页每请求的 DB 查询从 47 次降到 3 次，p95 1980ms → 180ms，p99 3400ms → 260ms，单机 4C8G 的 QPS 从 120 到 640。压测沿用了四月那套 200 并发、10 分钟的口径，只是把 JMeter 换成了 k6。五月末说「先把查询次数量清楚」，量完发现不用改 SQL，改的是调用方式。
- **三个工具 review 同一个 PR**：五月退了两个付费订阅，六月手上还能用的三个是留下的团队版、一个走 API 按量调的、一个本地模型。拿 DataLoader 那个 PR 各跑一遍，三个都喂同一份 diff、同一段 system prompt，评论导成 json 后按文件行号去重（去重脚本临时写的三十行，没进仓库）。一共 41 条评论，去重后 6 条是真问题，里面只有 2 条算真 bug（一条是 `CompletableFuture` 没处理异常、future 永不完成，一条是批量查询返回顺序没跟 key 对齐），剩下 35 条是格式建议和「建议加 JavaDoc」。
- **OOM**：02:14 告警、容器自己重启；02:19 确认没留下 dump；02:26 把 `HeapDumpPath` 改到新建的 20Gi PVC 上滚动重启，盯着等第二次；02:31 又 OOM，这回拿到完整的 2.7 GB hprof；02:40 用 `kubectl cp` 拖到一台 16 GB 的分析机上（本机 8 GB 根本打不开）。`ParseHeapDump.sh` 第一次没带 `-Xmx8g`，用默认堆跑了二十分钟自己先 OOM 了，重来一遍才出报告。dominator tree 里 `LocalBookCache` 的 `ConcurrentHashMap` retained heap 1.9 GB，塞了 71 万个 `BookDto`。换 Caffeine，`maximumSize(10000)` + `expireAfterWrite(10, MINUTES)`，一次发布搞定。
- **CI**：四月写「这条我打算塞进 CI」，五月写「还欠着」，这个月还了。`check_links.py` 一行没改，从手动挪进 workflow；另加一条校验 `search.json` 的脚本。第一次自动跑就报出 05-16 那篇里两张写错路径的截图，果然人肉会漏。
- **站点**：加四篇新文，索引从 17 篇、68 KB 涨到 21 篇、91 KB。

## 踩坑记录

**一、p95 两秒，不是 SQL 慢，是查了 47 次。** 四月把 Schema 改成按用例建类型之后，`shelf.books[].author` 每本书回表查一次，50 本书就是 50 次。压测脚本长这样：

```javascript
// tools/shelf.js —— k6 run tools/shelf.js（vus/duration 写在 options 里）
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 200,
  duration: '10m',
  thresholds: { http_req_duration: ['p(95)<300'] },
};

const QUERY = `query {
  shelf(userId: "u-1001") {
    books { id title author { name } stock }
  }
}`;

export default function () {
  const res = http.post('http://book-svc:8080/graphql',
    JSON.stringify({ query: QUERY }),
    { headers: { 'Content-Type': 'application/json' } });
  check(res, { '状态 200': (r) => r.status === 200 });
}
```

前后数字（同一台 4C8G、同一份脚本）：

| 指标 | 改之前 | 加 DataLoader 后 |
| --- | --- | --- |
| DB 查询 / 请求 | 47 | 3 |
| p95 | 1980 ms | 180 ms |
| p99 | 3400 ms | 260 ms |
| 单机 QPS | 120 | 640 |

47 次是怎么变成 3 次的：`shelf` 本身一次，`books[].author` 原来 N 次、现在用 `MappedBatchLoader` 把一整轮里的 author id 攒起来一次 `WHERE id IN (...)`，`stock` 同理再批一次。SQL 一行没改，慢的是「一次查一行」的调用方式。graphql-java 里 batch loader 返回顺序必须跟 key 列表严格对齐，顺序错了会静默地串数据，不报错。

第一版还翻过一次车：我把 `DataLoader` 注册成了全局单例，缓存跨请求复用，压测里 A 用户拿到了 B 用户的书架，看日志时后背一凉。graphql-java 的 `DataLoaderRegistry` 必须 per-request 建，改成每次请求 new 一份才对。这个错要是没压测直接上线，比慢 2 秒严重得多。

**二、dump 写不下的那个卷。** 启动参数是这么配的：

```yaml
# deploy/book-svc.yaml（出事那版）
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -Xms4g -Xmx4g
      -XX:+HeapDumpOnOutOfMemoryError
      -XX:HeapDumpPath=/dumps
      -XX:+UseG1GC
volumeMounts:
  - name: dump
    mountPath: /dumps
volumes:
  - name: dump
    emptyDir: {}          # 就是这里
```

`emptyDir: {}` 挂在节点临时卷上，`df -h /dumps` 一看：

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vdb        1.9G  712M  1.2G  38% /dumps
```

第一次 OOM 时 JVM 的报错：

```text
java.lang.OutOfMemoryError: Java heap space
Dumping heap to /dumps/java_pid1.hprof ...
Unable to create /dumps/java_pid1.hprof: No space left on device
```

改成 20Gi 的 PVC 之后，02:31 第二次 OOM 才拿到完整的 2.7 GB。顺带记一笔：MAT 解析 2.7 GB 的 hprof 自己要吃 6 GB 以上，`-Xmx8g` 是试出来的，不是算出来的。

**三、CI 里那条检查。** 部署 workflow 现在是这样，生成站点之后先过两道校验再 rsync：

```yaml
# .github/workflows/deploy.yml 片段
- name: 生成站点
  run: |
    npx hexo generate
    python3 tools/build_search.py
- name: 检查索引与坏链
  run: |
    python3 tools/check_links.py
    python3 tools/check_index.py
- name: 部署
  run: rsync -a --delete public/ deploy@static:/var/www/hexo/
```

`check_index.py` 是新写的，校验索引条数和落地页面一一对上：

```python
#!/usr/bin/env python3
"""校验 public/search.json 与生成出来的 HTML 一一对上。"""
import json
from pathlib import Path

public = Path("public")
index = json.loads((public / "search.json").read_text(encoding="utf-8"))
posts = list(Path("source/_posts").glob("*.md"))
if len(index) != len(posts):
    raise SystemExit(f"索引 {len(index)} 条，文章 {len(posts)} 篇，对不上")

bad = [e["path"] for e in index
       if not (public / e["path"].lstrip("/") / "index.html").exists()]
if bad:
    raise SystemExit("索引指向的页面不存在:\n" + "\n".join(bad))
print(f"ok: {len(index)} 条索引全部有页面")
```

输出 `ok: 21 条索引全部有页面`。四月的坏链脚本和这个一起挂上去，第一次跑还顺带把 05-16 那两张错图揪了出来。

> 顺带一提：三个工具里最勤快的那个提了 19 条，18 条是「建议给这个方法加 JavaDoc」，还有一条说 `DataLoaderRegistry` 拼错了、应该写成 `DataLoaderRegisty`。两条真 bug 是另外两个工具各报的，全被淹没在格式建议里。我现在先把 review 结果过一遍 grep，只看带「并发」「事务」「空指针」的。

## 还没解决的

- dump 卷换成 20Gi 了，但没做自动清理，两次 OOM 就是 5.4 GB，按月滚下去照样会满。想加个 sidecar 删 7 天前的 hprof，还没写。
- 180ms 是预热之后的值。服务刚重启那两分钟还是会弹到 400ms 以上，JIT 编译和 Caffeine 冷缓存各占多少，没拆开量过。
- 压测脚本里 `p(95)<300` 这个阈值是跑出 180ms 之后才填进去的，先射箭再画靶，下月按 SLA 重新定。
- 断更那周不补。
- 换掉 `ConcurrentHashMap` 之后，那 71 万个条目是半夜怎么涨起来的，还是没完全说清楚。MAT 能看到谁占着内存，看不到哪条请求路径在往里塞；日志里只有按小时的 cache size，没按接口拆。下回再 OOM 之前，得先把这个埋点加上。
