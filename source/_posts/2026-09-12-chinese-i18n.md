9 月 10 号早上 9 点 20，`npm run dev` 没起来，终端直接甩了一段：

> `GraphQLError: Names must match /^[_a-zA-Z][_0-9a-zA-Z]*$/ but "已支付" does not.`
> `    at assertValidName (/Users/youngcerulean/work/bookstore/node_modules/graphql/type/assertName.js:38:11)`

前一天我图省事，把订单状态枚举照着产品文案写成了 `enum OrderStatus { 已支付 已发货 已取消 }`。GraphQL 的 name 只认 ASCII，`assertValidName` 连服务都不让起。这已经是这个月第三次因为「中文放哪儿」返工了，当天下午干脆拉了 20 分钟会，定下一条土规矩：**面向用户的字符串全中文，代码标识符全英文**，谁都别再自由发挥。下面把这条规矩落到哪儿、踩过什么坑记一下。环境还是 `@apollo/server 4.10.0`、`graphql 16.9.0`、`typescript 5.5.4`。

## 规矩是怎么被逼出来的

4 月重写 Schema 的时候我顺手定过半条：`message` 写中文、`extensions.code` 用英文。当时只当是「别把英文渲染进 toast」的小事，没往深里想。结果 8、9 月连着出事：有人把中文塞进 enum，有人在日志里写整句中文，还有人把文案用加号拼成四段。三次都不是功能 bug，全是「同一份信息在不同层里各写各的」。

规矩拆开就两句话：

| | 给人看的 | 给机器看的 |
| --- | --- | --- |
| 内容 | 中文 `message`、前端文案字典 | 英文 `code`、结构化字段、日志 event |
| 放哪 | `GraphQLError.message`、`zh-CN.ts` | `extensions.code`、`logger.info({...})` |
| 改动频率 | 产品想改就改 | 定下来别动，报警规则依赖它 |

标识符（变量名、enum 值、错误码、日志 event、SQL 列名）一律英文；句子（toast、按钮、空状态、错误提示）一律中文，且只在用户看得见的层出现。顺带一提，这条跟写 Java 时「常量名大写英文、`MessageFormat` 管文案」其实是同一件事，换到 TS 里不知道怎么就散了。

定规矩那天还吵过「日志里能不能留中文」。有人说排障时看中文更直观，我的理由是日志的读者是机器和半夜被叫起来的运维，不是买书的人；真要给人看，前端页面和用户消息里已经够了。争了十来分钟，落到纸面上就成了「写进日志必须是英文 identifier 加数字字段」，谁写整句中文谁自己改。规矩不复杂，难的是四个人都记得住。

## 坑一：中文塞进 enum

开头那个报错就是它。修法也简单，enum 值回英文，中文放前端字典：

> `enum OrderStatus { PAID SHIPPED CANCELLED }` ← 能启动
> `enum OrderStatus { 已支付 已发货 已取消 }` ← `assertValidName` 直接拒

GraphQL 的 `description` 里写中文没问题（`"""已支付"""` 是文档，不是数据），但枚举**值**、字段名、类型名都不行，规范里 name 的正则卡死了。前端拿到 `PAID` 之后自己查 `zhCN['PAID']` 显示「已支付」。我第一版还想用 enum 值直接当文案省一次映射，被启动失败教育了。

## 坑二：日志里写中文，grep 直接瞎

原来我写的是 `logger.info(\`订单 ${orderId} 支付成功，金额 ${amount} 元\`)`。看着挺顺，等到想统计「每天多少人支付成功」就傻了：`grep -c '支付成功' app.log` 依赖一句文案不改，产品把「支付成功」改成「付款完成」历史数据全断；日志采集那边按空格切词，中文连成一坨，想按字段聚合根本没门。

改成结构化日志，中文一个字都不进：

> `logger.info({ event: 'ORDER_PAID', orderId, amountCents, durationMs })`

`event` 是英文常量，监控按它配报警，文案怎么改都不影响；`amountCents` 是数字，不用从句子里正则抠。改完当天就把一个「支付回调偶发 3 秒」的问题查出来了——以前中文日志里时间戳和金额混在一句里，翻起来眼睛都花。

## 坑三：拼出来的句子没法翻

前端第一版购物车的合计是 `'共 ' + n + ' 件商品，合计 ' + total + ' 元'`。要上英文版就得变成 `n + ' items, total ' + total`，量词、语序、复数全焊死在加号里，翻译拿到的是四段碎片，还没法处理「1 item」和「2 items」。

现在后端只给 `itemCount`、`totalCents` 两个数字，句子模板放前端，格式化交给 `Intl.NumberFormat`：

> `t('cart.summary', { count: itemCount, total: new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(totalCents / 100) })`

后端别拼句子，这条我拿 Java 的 `MessageFormat` 用了好多年的经验才反应过来，属实绕远路。

## 分层：code 英文、message 中文

落地就两块。先是前后端共用的英文常量，只有这一份，别的地方不许手写字符串：

```ts
// packages/shared/src/errorCodes.ts
export const ErrorCode = {
  BOOK_NOT_FOUND: 'BOOK_NOT_FOUND',
  BOOK_UNAVAILABLE: 'BOOK_UNAVAILABLE',
  OUT_OF_STOCK: 'OUT_OF_STOCK',
  NOT_LOGGED_IN: 'NOT_LOGGED_IN',
  ORDER_ALREADY_PAID: 'ORDER_ALREADY_PAID',
  INTERNAL_SERVER_ERROR: 'INTERNAL_SERVER_ERROR',
} as const;

export type ErrorCodeValue = (typeof ErrorCode)[keyof typeof ErrorCode];
```

然后是抛错的地方。这里还有个插曲：我照着 Apollo Server v3 的老教程写了 `import { ApolloError } from '@apollo/server'`，跑起来是

> `SyntaxError: The requested module '@apollo/server' does not provide an export named 'ApolloError'`

v4 里 `ApolloError` 这个类没了（以前在 `apollo-server-errors`），统一用 `graphql` 包的 `GraphQLError` + `extensions`。改完是这样：

```ts
// apps/api/src/errors/fail.ts
import { GraphQLError } from 'graphql';
import { ErrorCode, type ErrorCodeValue } from '@bookstore/shared/errorCodes';

export function fail(
  code: ErrorCodeValue,
  message: string,
  detail?: Record<string, unknown>,
): never {
  throw new GraphQLError(message, {
    extensions: {
      code,        // 英文，前端分流和监控报警都认它
      ...detail,   // bookId、stock 这类结构化字段，别拼进 message
    },
  });
}

// apps/api/src/resolvers/order.ts
import { fail } from '../errors/fail';
import { ErrorCode } from '@bookstore/shared/errorCodes';
import { logger } from '../logger';
import type { Context } from '../context';

export const Mutation = {
  createOrder: async (
    _p: unknown,
    args: { bookId: string; quantity: number },
    ctx: Context,
  ) => {
    if (!ctx.userId) {
      logger.warn({ event: ErrorCode.NOT_LOGGED_IN, path: 'createOrder' });
      fail(ErrorCode.NOT_LOGGED_IN, '登录后才能下单');
    }
    const stock = await ctx.db.stockOf(args.bookId);
    if (stock < args.quantity) {
      logger.info({
        event: ErrorCode.OUT_OF_STOCK,
        bookId: args.bookId,
        stock,
        want: args.quantity,
      });
      fail(ErrorCode.OUT_OF_STOCK, '库存不够了，先加入购物车，到货我提醒你', {
        bookId: args.bookId,
        stock,
      });
    }
    return ctx.db.orders.create(ctx.userId, args.bookId, args.quantity);
  },
};
```

`fail()` 收的 `message` 是中文，`code` 是英文常量，日志里只有英文 event 和数字。实测 `curl -s -X POST http://localhost:4000/graphql -H 'content-type: application/json' -d '{"query":"mutation { createOrder(bookId:\"bk_1042\", quantity:9){ id } }"}'` 拿到的响应：

```json
{
  "errors": [
    {
      "message": "库存不够了，先加入购物车，到货我提醒你",
      "locations": [{ "line": 1, "column": 12 }],
      "path": ["createOrder"],
      "extensions": {
        "code": "OUT_OF_STOCK",
        "bookId": "bk_1042",
        "stock": 2
      }
    }
  ],
  "data": null
}
```

## 后端不翻译，前端兜底

后端不读 `Accept-Language`，不切语言，永远只发这一份中文 `message` 加一个英文 `code`。真要上英文站，前端加一份 `en-US.ts`，后端一行不用改——这也是「后端不做翻译」的意思。

前端按 `code` 查自己的字典，命中就用；没命中（比如第三方服务抛的、没有 code 的错）就沿用后端的中文 `message`；连 `message` 都没有，再兜一句通用的：

```ts
// apps/web/src/i18n/errorMessage.ts
import { ErrorCode, type ErrorCodeValue } from '@bookstore/shared/errorCodes';

const zhCN: Record<ErrorCodeValue, string> = {
  BOOK_NOT_FOUND: '没找到这本书，可能已经下架了',
  BOOK_UNAVAILABLE: '这本书暂时买不了，看看别的吧',
  OUT_OF_STOCK: '库存不够了，先加入购物车，到货我提醒你',
  NOT_LOGGED_IN: '登录后才能下单',
  ORDER_ALREADY_PAID: '这笔订单已经付过了，别重复点',
  INTERNAL_SERVER_ERROR: '服务开了点小差，稍后再试',
};

const fallback = '出了点问题，稍后再试';

interface GraphQLErrorLike {
  message: string;
  extensions?: { code?: string };
}

export function messageOf(error: GraphQLErrorLike): string {
  const code = error.extensions?.code;
  if (code && code in zhCN) return zhCN[code as ErrorCodeValue];
  return error.message || fallback;
}

export function needsLogin(error: GraphQLErrorLike): boolean {
  return error.extensions?.code === ErrorCode.NOT_LOGGED_IN;
}
```

有人问过「后端都发中文了，前端这份字典不是重复吗」。不重复：后端那份是给小程序、给没接字典的调用方兜底的，前端这份才是产品能随时改、能换语言的唯一来源。两份靠英文 `code` 对齐，谁改文案都不用动对方。顺带一提 Web 和小程序现在共用 `packages/shared` 里那份 `ErrorCode`，改常量名两边一起编译报错，比从前各存一份字符串强太多。

## 还没解决的

三个坑里第三个只清了购物车，订单详情页还留着几处模板字符串在拼句子（`顺丰已揽收，预计 ${date} 日送达` 这种），得一个个拆成结构化字段加模板。另外 `ErrorCode` 现在 6 个常量挤在一个对象里，等涨到 20 多个要不要按域拆成 `BOOK_*`、`ORDER_*`、`USER_*` 还没定，拆早了纯属给自己找事。

更卡住的是监控那边：报警规则按 `extensions.code` 配的，可 `OUT_OF_STOCK` 到底是用户手滑多点了几本，还是库存服务同步慢了，一直分不出来，报警响了一半是噪音。要不要在 `extensions` 里再加个 `retryable: boolean` 或者 `origin` 区分一下，我还没想好，先停在这。
